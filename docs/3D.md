# 3D in Replay: a plan

Status (2026-11-05): decided (§9), phases 1 to 3 built (§10 to §12). The rest
is the plan.

**Goal**: 3D without PBR. That means vertex colours, textures, one sun with
shadow maps, and an ambient term. The importers are FBX (ufbx), glTF 2.0
(cgltf), MagicaVoxel (ogt_vox) and IQM (fwk's loader, skeletal animation).
It has to fit how Replay works: the world is a tree of plain data, edited
live, rewound on a timeline and drawn by the host. Later on top of it: the
pre-rendered rooms plugin (albedo and depth backgrounds, as in LBA or Alone
in the Dark) and the 3D draw modes the other engine has (x-ray, silhouette,
outline, decals).

## 1. Where things are today

- `editor/render.h` draws the world with SDL's 2D renderer
  (`SDL_RenderGeometry`: triangles, textures, batches). The game area is a
  render target. The editor's overlays and Lite (a software renderer into a
  texture) are drawn on top of it.
- Every test runs with `SDL_VIDEODRIVER=offscreen`. This container has no
  GPU, and `SDL_CreateGPUDevice` fails there ("No supported SDL_GPU backend
  found"). That shapes the test plan (§7).
- `c:\prj\game\src` (r-lyeh's other engine) already does part of this on
  SDL_gpu: a 2D batcher plus depth-tested 3D shapes (spheres, cylinders,
  capsules, convex polygons, instanced). Its depth fill writes a
  pre-rendered background's depth image (`DPT1`, half floats, meters) into
  the depth buffer, so 3D figures hide behind the background's objects. It
  also has x-ray, mask, outline and decal pipelines, and camera math
  (`cam3d.h`: right-handed, z up, depth 0..1). Its shaders are HLSL,
  precompiled to SPIR-V and DXIL and embedded as headers. It has no Metal
  build, so no macOS.

## 2. The draw path: three choices

| | SDL_gpu (SDL3) | OpenGL 3.3 / GLES 3 | a CPU rasterizer |
|---|---|---|---|
| Backends | Vulkan, D3D12, Metal | GL everywhere (on macOS: deprecated, 4.1) | none needed |
| Shaders | one per backend format: SPIR-V, DXIL, MSL (precompiled with SDL_shadercross, or translated at run time) | GLSL, one source | C |
| With today's 2D | `SDL_CreateGPURenderer(device, window)` (SDL 3.4, the version we ship): the 2D renderer runs on our GPU device, and our 3D passes share it | the 2D renderer forced to its GL backend, with GL state shared around it: brittle | draws into a texture the 2D renderer shows |
| Speed | best | good | fine for a few thousand triangles at low resolution |
| Tests here | no GPU in CI: needs lavapipe (Mesa's software Vulkan) installed, or a fallback | needs Mesa llvmpipe | runs everywhere |

**Recommended: SDL_gpu with `SDL_CreateGPURenderer`, plus a small CPU
rasterizer as the fallback.**

- SDL_gpu is where SDL3 is going. The other engine already proves it with
  the same libraries, and it reaches Metal, which GL doesn't, really. With
  `SDL_CreateGPURenderer`, render.h's 2D code stays as it is and the 3D
  passes record into the same command buffer.
- The CPU rasterizer (flat and Gouraud shading, a z-buffer, textures,
  nearest filtering) has three jobs:
  - it draws when there's no GPU: the CI here, old machines, headless shots;
  - it makes tests deterministic, with pixels compared;
  - it is the reference that the GPU output is checked against.

  It's about 400 lines in C. Lite is proof that a software path is fine for
  small pictures.

## 3. How 3D fits the tree: a viewport node

**Recommended:** a 3D scene is drawn through a node with a `camera3d`
component. It renders the 3D nodes under it into an offscreen texture of its
size, and that texture is the node's picture in 2D. Everything 2D keeps
working around it:

- layers, the HUD on top, picking (a right-click on the viewport picks the
  3D node under it, by a ray), the editor's eye and overlays;
- several viewports at once (split screen, a minimap, a portrait).

```lua
w:spawn("/objects/view", { transform = { x = 0, y = 0 },
  camera3d = { w = 640, h = 360, fov = 60, near = 0.1, far = 200,
               eye = { 0, 3, 8 }, at = { 0, 1, 0 },         -- or a camera node: follow = "/objects/view/cam"
               clear = { 40, 44, 52 }, ambient = { 60, 60, 70 },
               sun = { dir = { -0.4, -1, -0.3 }, color = { 255, 244, 220 }, shadows = 2048 } } })
w:spawn("/objects/view/ship", {
  transform3d = { x = 0, y = 0, z = 0, ry = 0.5, s = 1 },      -- meters, radians (or q = { x, y, z, w })
  mesh = { "/assets/ship.glb", color = { 255, 255, 255 }, texture = nil, shadows = true },
  animator = { clip = "idle", t = 0, speed = 1, loop = true } })   -- skinned meshes: the pose comes from the clip at t
```

- **Components:**
  - `camera3d`;
  - `transform3d` (children follow);
  - `mesh` (a file of `assets/` and, optionally, a node or mesh inside it:
    `part = "wheel"`);
  - `animator` (plain data: `t` advances in a system, so a rewind brings
    the pose back);
  - `light3d` later (points: a few, no shadows);
  - the shapes as components (`sphere3d`, `box3d`, `capsule3d`), for blocking
    out a level and for debug.
- **Data stays plain:** the world holds paths and numbers, the host caches
  the GPU buffers. That's how `image` and `tilemap` work now, so save, diff,
  replicate and rewind work unchanged.
- **Systems:** `w:pick3d(view, x, y)` returns the node and the point hit.
  `w:project3d(view, x, y, z)` returns screen x and y (the other engine's
  `gfx_project3d`). `anim3d.clip_length(mesh, clip)` and the clips' names.

The alternative, the whole game area being 3D with 2D drawn over it, is
simpler for a pure 3D game. But it gives up split screens, minimaps and 3D
inside a 2D UI, and it changes what picking and the eye mean. A
`camera3d` the size of the window gives that case anyway.

## 4. Rendering

1. **Pass order, per viewport:**
   - the shadow map: the sun's depth, 2048 px, one cascade fitted to the
     viewport's view;
   - the opaque meshes: depth tested;
   - the alpha-tested meshes (foliage);
   - the 3D debug draw (`dd3.line`, `dd3.box`);
   - the result goes into the viewport's texture, and the 2D pass draws it.
2. **Lighting:** Lambert from the sun, plus ambient, plus vertex colour,
   times the texture. The shadows are PCF 3x3. Optional: hemispheric ambient
   (a sky colour and a ground colour), and fog (linear, a colour).
3. **Pipelines:** static, static with vertex colours, skinned (64 bones:
   uniforms; more: a storage buffer). Each has a shadow variant, and the
   other engine's modes (x-ray, silhouette mask, outline, decal) come later
   as variants too. Sprite outlines in 3D (the 2D `outline1` / `outline2`)
   use the same approach: a stencil mask, then the mesh inflated.
4. **Shaders:** HLSL sources in `editor/shaders/`, precompiled offline with
   SDL_shadercross to SPIR-V, DXIL and MSL, and checked in as headers (the
   other engine does this without MSL). A missing format means no GPU path
   on that system, and the CPU fallback draws instead. Players never need
   the shader compiler.

## 5. Importers: one mesh format

All four importers turn their file into one in-memory form, `Mesh3D`:

- vertex buffers (position, normal, uv, colour, joints and weights);
- index ranges, one per material, with a base colour and a texture name;
- a node hierarchy;
- a skeleton (inverse bind matrices);
- clips (per-joint keys: translation, rotation, scale; linear and slerp).

The formats (all single C files):

| Format | Library (licence) | What comes along |
|---|---|---|
| glTF 2.0 (`.gltf`, `.glb`) | cgltf (MIT) | meshes, base colour texture and factor, vertex colours, skins, animations, embedded images (decoded by images.h) |
| FBX (`.fbx`) | ufbx (MIT / public domain) | meshes, materials' diffuse, skins, takes as clips |
| MagicaVoxel (`.vox`) | ogt_vox (MIT / public domain), meshed greedily (ogt_voxel_meshify) | the palette as vertex colours, several models, the scene's transforms |
| IQM (`.iqm`) | fwk's loader (r-lyeh: public domain / MIT) | meshes, skeleton, clips (the format is made for skeletal animation). *Postponed (r-lyeh, 2026-11).* |

Import happens at load. It's cached by the file's change time, and read
again when the file changes (as images are). Cooking these into a packed
form is the content pipeline's job (postponed).

## 6. The editor

- **The model viewer (the first deliverable):** a new plugin,
  `plugins/modelview`, a tab (Graphics >) that opens `.glb`, `.gltf`, `.fbx`,
  `.vox` and `.iqm`.
  - Controls: orbit (LMB), pan (MMB), zoom (the wheel).
  - Panels: the node tree, the materials, the clips (play, scrub), the
    skeleton drawn over the model, wireframe and normals.
  - It draws with the same code as games. Lite can't draw 3D, so the
    plugin gets its picture from the host through a `host_render3d(...)`
    texture, as the game view does.
- **In the game view:** a `camera3d` node can be flown in the editor with
  RMB and WASD, and that doesn't change the game's camera. A right-click
  picks a 3D node. A move / turn / scale gizmo comes later.
- **The tree:** `+ mesh` in `/assets` imports a file, and an asset row
  shows a thumbnail rendered once.

## 7. Tests

- The importers, in Lua-visible C: each format's sample loads. The tests
  check the counts (vertices, materials, joints, clips), a clip's pose at
  t = 0.5 against known matrices, and that the voxel meshing is watertight.
- The CPU rasterizer: shots compared to expected pixels (a lit cube, a
  textured quad, a shadow on a plane, a skinned arm bent at 90°). They run
  in CI here.
- The GPU path: the same scenes, compared to the CPU output within a
  tolerance. These run where a GPU, or lavapipe, exists. In this container
  we can try installing Mesa's lavapipe; if that fails, the GPU tests skip
  here and run on your machine.
- Samples, CC0, made by scripts as the slime was: a cube, a low-poly ship
  (glTF), a two-bone arm with one clip (IQM and glTF), a voxel house (vox).

## 8. Phases

Each phase ends with a full test run, the docs and a sync.

1. **The spike:**
   - an SDL_gpu device, plus `SDL_CreateGPURenderer` in replay.c;
   - the 2D renderer on it, with the whole suite unchanged (the CPU
     fallback is the plain renderer, as now);
   - `--gpu off | vulkan | d3d12 | metal` on the command line.
2. **The meshes:** `Mesh3D`, the glTF importer, and the CPU rasterizer
   (unlit, vertex colours, textures, the z-buffer). Then `camera3d`,
   `transform3d` and `mesh`, drawn by the CPU path into the viewport's texture.
3. **The GPU path:** the same scene on the GPU, the shaders (HLSL to
   SPIR-V, DXIL and MSL), Lambert, the sun, ambient, fog.
4. **Shadows:** a shadow map (GPU) and a shadow buffer (CPU).
5. **Skinning:** the `animator` component, glTF skins, IQM, clips (CPU
   skinning first, then GPU).
6. **FBX and vox:** ufbx, and ogt_vox with meshing.
7. **The model viewer plugin:** orbit, clips, the skeleton, thumbnails.
8. **Afterwards:** picking and project3d, the editor's fly camera, gizmos,
   the x-ray, outline and decal modes, and the pre-rendered rooms plugin
   (depth backgrounds: the other engine's `DPT1` and depth fill).

The first three phases are the bulk of the risk. Everything after them adds
to a path that already works.

## 9. Decisions (r-lyeh, 2026-11-05)

1. **The draw path:** SDL_gpu, with the CPU rasterizer as the fallback.
2. **Axes:** y up, right-handed, meters. The importers convert z-up files.
3. **How 3D fits the tree:** `camera3d` viewport nodes.
4. **Shaders:** precompiled and checked in (`editor/shaders/*.h`).
5. **macOS:** asked what the problem would be; see §9.1. Proposed: MSL in the
   shader build from the start, untested until someone runs it on a Mac.
6. **The first deliverable:** the model viewer plugin (phases 1, 2, 3, then 7).

### 9.1 macOS: what it costs

There's no blocker. SDL_gpu's Metal backend is as complete as its Vulkan
one, and the 2D renderer already runs on it. What it takes:

- **Shaders in MSL as well.** spirv-cross turns our SPIR-V into MSL, so the
  build makes all formats from one source. That's cheap and done from the
  start.
- **Formats that Apple GPUs have.** Apple Silicon has no 24-bit depth
  (`D24_UNORM`), so depth is `D32_FLOAT` (with `_S8_UINT` when the outline
  pass needs a stencil) on every backend. Also: no geometry shaders (we
  don't need any), and storage buffers bind by index on Metal. SDL hides
  most of that if we keep to its common subset.
- **Testing is the one real cost.** No Mac here, and lavapipe is Vulkan
  only. So Metal bugs would show only on a Mac, until someone runs the
  tests there. If Metal fails at start, the CPU fallback draws instead, so a
  Mac never gets a black window.
- **Building Replay for macOS** (an app bundle, SDL3 for macOS, signing to
  share it) is a separate step, and not 3D's. The code already handles Cmd+Q.

### 9.2 The shader build

`editor/shaders/*.hlsl` (or `.glsl`) are the sources.
`editor/tools/shaders.sh` and `editor/tools/shaders.bat` build them, and the outputs are
checked in as headers. Who makes what:

| Format | Backend | Made with | Where |
|---|---|---|---|
| SPIR-V | Vulkan (Windows, Linux, Android) | glslangValidator (its HLSL front end too) | here, or anywhere |
| MSL | Metal (macOS, iOS) | spirv-cross, from the SPIR-V | here, or anywhere |
| DXIL | D3D12 (Windows) | DXC (the Windows SDK) | r-lyeh's machine (`editor/tools/shaders.bat`) |

GitHub is closed to this workspace, so it can't get DXC. Until a DXIL build
is checked in, Windows uses Vulkan: the device is asked for SPIR-V and MSL
only, so SDL never picks D3D12 without shaders for it. Almost every Windows
GPU of the last ten years has Vulkan. `--gpu direct3d12` becomes useful
once the DXIL headers exist.

## 10. Phase 1: built (2026-11-05)

- `editor/gpu.h`: `gpu_create_renderer(win)`. It makes an SDL_gpu device,
  then `SDL_CreateGPURenderer(device, window)`. All the 2D (render.h, the
  editor, Lite's texture) runs on it unchanged, and `g_gpu` is the device
  the 3D passes will share. No device, or its renderer fails, or `--gpu
  off`: SDL's own renderer, as before.
- `--gpu auto | off | vulkan | direct3d12 | metal` on the command line.
  `--shot` prints the renderer and the GPU driver
  (`renderer: gpu (gpu: vulkan)`).
- **Tests:** Mesa's lavapipe (software Vulkan) is installed here
  (`apt-get install mesa-vulkan-drivers`). With it, the full suite (141
  suites) passes on the GPU renderer.
  - asteroids' frame 90 on the GPU renderer and on SDL's own differs in 82
    pixels out of 600,000: the fps counter, and rounding at shapes' edges.
  - The suite runs on the GPU path when a Vulkan driver is present, and on
    SDL's own renderer when not. `--gpu off` forces SDL's own.

## 11. Phase 2: built (2026-11-05)

- **`editor/mesh3d.h`:** `Mesh3D`, as §5 says (positions, normals, uvs,
  colours, indices; parts with a base colour and a texture), cached by its
  file's change time.
  - glTF 2.0 by cgltf 1.14 (MIT: `editor/3rd/models/`, beside ufbx since phase 6). Every node's mesh
    is baked at the node's world transform (normals by the inverse
    transpose). It reads COLOR_0, TEXCOORD_0, and the base colour factor
    and texture; textures can be embedded or files beside the model,
    decoded by images.h.
  - The built-in shapes: `cube`, `plane`, `sphere`.
- **`editor/raster3d.h`:** the CPU rasterizer. Column-major matrices, y up,
  clip depth 0..1. Triangles are clipped at the near plane, and the ones
  facing away are culled. Lambert from the sun plus ambient, per vertex;
  textures per pixel, perspective-correct, nearest; alpha tested.
- **`render.h`:** the `camera3d` component. Its subtree's `transform3d` and
  `mesh` nodes are drawn into its picture (an RGBA buffer, uploaded to a
  streaming texture), then drawn as a quad of the 2D world, with picking.
- **The demo:** `games/spin3d.lua`, a glTF ship (vertex colours, two
  nodes), a glTF crate (an embedded texture), built-in shapes, keys to
  orbit. The samples come from `games/common/tools/make_models3d.py` (CC0).
- **Tests** ("3d viewport"):
  - built-in shapes lit flat, so the colours are exact;
  - near-plane clipping;
  - culling (the camera inside a cube);
  - nested `transform3d`;
  - a texture;
  - the two glTF files read (counts, the embedded texture's size);
  - a missing model says why.

  The hooks: `host_camera3d(path, x, y)` and `host_mesh3d(name)`.

## 12. Phase 3: built (2026-11-05)

- **The shaders:** `editor/shaders/mesh.vert` and `mesh.frag` (GLSL 450).
  They do what raster3d.h does: Lambert from the sun plus ambient per
  vertex, times the vertex colour and the base colour; the texture per
  pixel, nearest, repeating, alpha tested at 0.5.
  - `editor/tools/shaders.sh` builds them into checked-in headers
    (`mesh_vert.h`, `mesh_frag.h`): SPIR-V by glslangValidator, MSL by
    spirv-cross.
  - The device asks for SPIR-V and MSL only, so Windows runs on Vulkan
    until DXIL exists (§9.2).
- **`editor/render3d.h`:**
  - One pipeline: one vertex buffer of 36 bytes a vertex (position, normal,
    uv, colour as 4 bytes), back faces culled, depth `D32_FLOAT` (else
    `D24`).
  - A mesh's GPU copy (vertex and index buffers, its textures) is made once
    and made again when its file is read again; a node's `texture = "..."`
    is kept by its file.
  - Each viewport has its own colour and depth textures. Its draws go into
    a command buffer of their own, submitted at once, and the colour
    texture is wrapped as an `SDL_Texture`
    (`SDL_PROP_TEXTURE_CREATE_GPU_TEXTURE_POINTER`), which the 2D renderer
    draws like any picture.
  - Everything is released before the device goes (`g_gpu_release`).
- **Which one draws:**
  - The GPU, when `g3_init` succeeds: a device, shaders for its backend,
    the pipeline.
  - Else the CPU, and also when `camera3d = { cpu = true }` or the
    `REPLAY_3D=cpu` environment variable is set.
  - `host_render3d()` says which one, and why.
- **Tests:** "3d viewport" runs its checks twice, on the GPU (lavapipe here)
  and on the CPU (`REPLAY_3D=cpu`), with the same exact colours. Reading
  the GPU's picture back for the hook (`host_camera3d`) waits for a fence.
  spin3d's frame 40 differs between the two in 1 pixel out of 256,000.
- **Next:** phase 4 (shadows), or phase 7 first (the model viewer, the
  first deliverable). Phase 7 needs Lite to show a host-drawn picture.

## 13. Phase 7: the model viewer, built (2026-11-05)

- **The hole.** A Lite tab can't hold a GPU texture (its picture is a
  CPU surface), and reading the GPU's picture back every frame costs. So
  Lite leaves a hole: `renderer.clear_rect(x, y, w, h)` (a lite.h patch,
  docs/PATCHES.md) sets those pixels to alpha 0. The host draws the 3D
  view first and Lite's picture over it, blended (replay.c's compose,
  `lite3d_draw` in render.h). Menus and tooltips over the view are Lite's,
  so they stay on top. kit's PBR demo does the same compositing: an
  offscreen target, wrapped, drawn by SDL_Renderer, and opaque
  (`SDL_BLENDMODE_NONE`, as here).
- **The hooks** (editor.h, in Lite):
  - `host_view3d{ key, file, x, y, w, h, eye, at, up, fov, clear, ambient,
    sun = { dir, color } }` asks for a view in Lite's pixels; it stays
    until `{ key, remove = true }`.
  - `host_model_info(file)` returns `{ vertices, indices, min, max, parts =
    { { base, texture, triangles } }, textures = { { w, h } } }`, or nil and
    why.
  - `host_view3d_pixel(key [, x, y])` returns w, h, triangles and r, g, b, a,
    for tests.
  - Up to 8 views. Each is drawn again only when its request or its model
    changes, on the GPU (`G3View`) or the CPU (`R3Target` and a streaming
    texture).
  - `mesh3d_get` takes `file:<path>` for a file anywhere.
- **plugins/modelview:**
  - `.gltf` and `.glb` files.
  - Orbit (LMB), pan (MMB or Shift+LMB), zoom (the wheel), fit
    (double-click or F).
  - The panel: vertices, triangles, size, parts, textures.
  - It wraps `renderer.begin_frame` and `end_frame`, so a view that isn't
    drawn in a frame (a tab behind another, a closed one, Lite hidden) is
    removed from the host.
- **Tests:** modelview_edit (13 checks: the crate's counts, the picture's
  size, wood in the middle, the background in the corner, orbit, fit, gone
  behind another tab and back, a missing file says why). It passes on the
  GPU and with `REPLAY_3D=cpu`.

## 14. Phase 4: shadows, built (2026-11-05)

- **The API:** `camera3d.shadows = true`, or `{ size = 1024, area = m }`.
  `size` is the map's texels (64 to 4096). With `area`, only that many
  meters round `at` are covered, for big scenes; otherwise the whole
  scene is.
  - Lite views: `host_view3d{ shadows = true, ground = true }`. `ground`
    puts a floor under the model.
- **The sun's view** (`s3_sun_fit`, `r3_sun_fit`): orthographic, fitted to
  the sphere round the items' bounds (their 8 corners, transformed).
  - Depth runs 0..1 over 3 radii.
  - Bias: one texel of depth.
  - Normal offset: a texel and a half along the normal, in the world.
    This is what removed the acne on curved surfaces.
- **The test, the same on both:** each pixel's light-space position is
  interpolated (perspective-correct on the CPU). Then 9 texels (PCF 3x3)
  are read by integer index (`texelFetch` on the GPU), each lit when `z -
  bias <= depth`. The sun's share of the colour, interpolated beside the
  full colour, is taken away times the unlit fraction. With no shadows
  the colour is the old one, bit for bit.
- **GPU** (render3d.h):
  - A depth-only pass first, into the view's shadow map. It uses its own
    pipeline: mesh.vert with the sun's matrix, `shadow.frag` empty, no
    culling.
  - The colour pass samples the map at fragment sampler 1. Its
    parameters are a fragment uniform (set 3).
  - When the depth format can't be sampled there's no `shadow_pipe`, and
    no GPU shadows.
- **CPU** (raster3d.h): the items are collected first, now also on the CPU
  path (`G3Item.cpu_tex`). Then `r3_shadow_draw` fills one depth map shared
  by all CPU views, and `r3_draw` tests it.
- **Not yet:**
  - Alpha-tested casters cast solid shadows (the shadow pass doesn't
    alpha test).
  - One cascade.
  - No hemispheric ambient or fog yet.
  - Metal reads the depth map through `texture2d` (what spirv-cross
    gives); not tried on a Mac.
- **Tests:**
  - "3d viewport": a cube over a floor with the sun slanting, seen from
    above. Its shadow is 60 (ambient only) and the lit floor 240, ±1, on
    the GPU and on the CPU.
  - spin3d's frame: 2 pixels out of 256,000 differ between the two.
  - modelview_edit: the floor is darker with shadows; without the floor,
    the background shows.

## 15. Phase 5: skinning, built (2026-11-05)

- **Read** (mesh3d.h, cgltf):
  - The first skin a mesh node has. Its vertices stay in bind space; the
    node's transform is ignored, as glTF says. Up to 4 joints and weights
    a vertex (normalized), at most 255 joints.
  - The joints: parent (among the joints), rest translation, rotation and
    scale (or a matrix), and the inverse bind matrix. A root joint's
    ancestors that aren't joints go into its `base`.
  - Every animation's channels on joints become a `Clip3D`: keys per joint
    and path. Step and linear; cubic splines use their keys' values,
    linearly.
  - Not read yet: weights (morph targets), channels on nodes that aren't
    joints, a second skin.
- **Posed** (`mesh3d_pose`, `mesh3d_skin`, `pose3d_get`):
  - The clip is sampled at t (slerp for rotations; wrapped when looping),
    parents first, then joint world times inverse bind.
  - Each vertex is moved by its 4 weighted matrices, its normal too
    (normalized).
  - A posed copy is kept for each key (a node's path, a lite view). It
    shares the base's arrays except positions and normals, so both drawers
    draw it like any mesh.
  - The GPU re-uploads only its vertex buffer (cycled) when its version
    moves. GPU skinning (joints in a uniform or storage buffer) is later,
    when there are many characters.
- **The API:**
  - `animator = { clip = "bend" | n, t = s, loop = true }` on a mesh node.
    The game moves `t`, so a pose is data (saved, rewound, sent like any
    component).
  - Model viewer: `host_view3d{ clip, t, loop }`; `host_model_info` gives
    `joints` and `clips`.
  - Tests: `host_pose3d(name, clip, t, vertex)` and `host_mesh3d`'s 7th
    and 8th values (joints, clips).
- **The sample:** games/common/arm.glb (make_models3d.py), a 2 m post with
  two joints and a clip, "bend": the lower joint turns 90° about z in 1 s.
- **Tests:**
  - "3d viewport": the tip's vertex is (-1, 0.88, -0.12) at 1 s and
    (-0.792, 1.622) at 0.5 s; the bent arm's pixels on the GPU and the CPU.
  - spin3d: the GPU and CPU frames still differ in 2 pixels.
  - modelview_edit: the arm's joints and clip, it plays, scrubbing moves it.
- **Next** (phase 6, with FBX and vox): IQM (its skeleton and clips go into

## 16. Phase 6 (part): FBX by ufbx, built (2026-11-05)

- **The library:** ufbx 0.23.1 (MIT or public domain) in `editor/3rd/models/`,
  beside cgltf (moved there from `3rd/cgltf/`). `ufbx.c` is compiled into
  replay.c's unit through mesh3d.h, so make.bat doesn't change. The build
  here takes about twice as long.
- **Read** (`mesh3d_fbx`):
  - Loaded with y up, right-handed, in meters (ufbx converts axes and
    units).
  - Visible meshes only: a CAT rig's 16 helper boxes are hidden in the
    file.
  - Triangulated, each corner its own vertex. Positions are placed at the
    node's `geometry_to_world`, normals by its normal matrix; uv flipped (v
    goes up in FBX); vertex colours.
  - A part per material: the base colour and its texture, embedded or a
    file, as written or by its name beside the model. A texture isn't
    dimmed by FBX's usual 0.8 diffuse.
- **Skins** (into phase 5's form):
  - The joints are every cluster's bone and its ancestors, the scene's root
    left out, parents first by depth.
  - Each cluster is a *bind*: its joint, and an inverse bind matrix =
    `geometry_to_bone` × the node's place inverted (the vertices are
    already there). That's why `Mesh3D` now has binds besides joints, and
    `jnt` is 16-bit. glTF has a bind a joint.
  - Each vertex keeps its 4 heaviest weights, normalized.
- **Clips:** each animation stack is sampled a frame at a time at the
  file's rate (`frames_per_second`): every joint's translation, rotation
  and scale by `ufbx_evaluate_transform`, linear between frames.
- **Sub-clips** (`mesh3d_animlist`, for both formats):
  - Read from `<file>@animlist.txt`, then `animlist.txt` beside it. A line
    `frame: 66-85 Run (Loop)` makes a clip of those frames of the first
    clip (glTF: 30 fps).
  - "(Loop)" is taken off the name and kept as `loops`.
  - A line covering the whole take again, or a name already there, is left
    out.
  - `Clip3D.src` and `start` point into the take's keys.
- **The sample:** `games/common/kgirl/` ("kgirls01" by nanofactory, CC
  BY-NC-ND 4.0: credited, not changed, not for commercial games;
  LICENSES.md).
  - 9426 vertices, 4 parts, a 1024² texture, 34 joints.
  - 27 clips: "Take 001" and the animlist's 26.
  - Its demo is games/kgirl3d.lua (clips with left and right, orbit with
    A and D).
  - The model viewer opens `.fbx` too.
- **Tests:**
  - "3d fbx": the counts; "Run" at 0.1 s is the take at frame 66 plus
    0.1 s, to 1e-5; meters, y up; drawn.
  - modelview_edit: the FBX's parts, texture, joints, clips and size.
  - kgirl3d on the GPU and the CPU: 20 pixels of 256,000 differ by more

## 22. The transform gizmo, built (2026-11-05)

One gizmo, editor/tgizmo.h, worked out in 3D. A 2D node is the special case: seen from the front, orthographic, y down, so it drops the z arrow and the x / y rings.

- **Where it goes:** render.h records the selection's place as it's drawn: draw_node gives the composed 2D Mat, draw3d_node gives the world matrix, its parent's, and the camera3d it's under. A 3D node wins over the 2D walk that passes through it afterwards. replay.c draws the gizmo after the selection box and gives it LMB presses in the game view before node dragging (move_start). It only works when stopped or paused, never standalone.
- **Its view:** `tg_view` projects the origin and each axis (move and rotate use world axes; scale uses the node's own). On screen each axis is a direction plus a length: an axis seen end-on gets shorter and isn't grabbable. Points per meter come from a step across the view at the node, so the handles keep a constant size (70 px arrows, 55 px rings). That size is shrunk by `g` when the rings would reach the camera, which happens in small views.
- **Move:** in 2D, screen delta / zoom, locked to an axis, through `viewer_move_by`. In 3D, the nearest point on the axis line to the first ray and to the current one; the free square uses the plane through the node that faces the camera. The world delta is brought into the parent's space.
- **Rotate:** the screen angle round the origin. In 3D it's negated when the axis points at the viewer. R' = Rot(axis in parent space) · R, then decomposed back into Ry·Rx·Rz (rx = asin(-r12), ry = atan2(r02, r22), rz = atan2(r10, r11); at gimbal lock it all goes into ry). Of the two equivalent angle sets, it keeps the one nearer the start, so there are no flips.
- **Scale:** the factor is 1 + the drag along the handle / its length, per local axis (2D: `dsx` / `dsy`) or even (the square).
- **Totals, not steps:** 2D applies the difference from what's been applied so far, and 3D sets the start value plus the total (`viewer_move3d_set`), so Ctrl snapping lands on exact steps.
- **Undo:** `viewer_move_end` rounds (transform3d too) and records one level.
- **Tests:** `host_gizmo("select" | "show" | "mode" | "info" | "press" | "drag" | "release")`; the suite "transform gizmo" covers hop (move along x, 90°, x scale) and view3d_game's cube (move along x, y scale, a turn about z).

## 23. GPU skinning, instancing, foliage (2026-11-05)

- **Instancing.** mesh.vert takes each copy's model matrix and tint per instance (vertex buffer 1, instance rate; G3Instance, 80 bytes). Its normals' matrix is worked out in the shader. g3_render orders the view's items (skinned last; then by mesh and the texture over it), uploads one instance buffer for the frame in a copy pass, and draws each run of the same mesh as one instanced draw per part (the instance buffer bound at the run's offset). The shadow pass draws the same way.
- **GPU skinning.** mesh_skin_vert.h is the same source with SKIN defined (shaders.sh builds the variant). It has 4 binds and weights per vertex (vertex buffer 2, G3SkinVertex, uploaded once per model) and up to 256 skin matrices in uniform buffer 1, pushed per item.
  - draw3d_node sets `pose3d_gpu` around pose3d_get. With it set, the posed copy carries only its matrices (`gpu_mats`) and the base's unskinned vertices (`gpu_base`), so there's no per-frame vertex upload.
  - A blend shape that is weighted, or more than 256 binds, falls back to the CPU as before.
  - Anything on the CPU that needs the posed vertices (a ray pick, the outline's silhouette) calls `pose3d_cpu`, which skins it then, once.
  - The model viewer and host_pose3d still pose on the CPU.
  - 60 animated kgirls: game 310 ms down to 44 ms a frame in the cloud (lavapipe); poses3d grew from 32 to 256 slots, g3meshes to 128.
- **Foliage.** runtime/foliage.lua: a .foliage's layers scattered over w x d m. Park-Miller random numbers and value-noise clumps, all exact in doubles, so LuaJIT and 5.4 make the same scatter.
  - A node's `foliage3d` (`{ "file", overrides }` or the settings themselves) goes through boot.lua's viewer_foliage → w:foliage (cached by its text and overrides) → render.h draw3d_foliage.
  - draw3d_foliage reads the arrays once per scatter (Foliage3D, keyed by the items table) into local matrices and tints, then adds a G3Item per copy every frame: one instanced draw per layer part.
  - The CPU rasterizer draws each copy.
  - plugins/foliage is the editor, seen from above.
- **host_camera3d fix:** with no x, y it read its own pushed w, h as a pixel (a bug since it was written). It now also returns the GPU's draw calls and "gpu" / "cpu".

## 24. Grass in 3D, after Outerra (2026-11-05)

After Outerra's "procedural grass rendering" (2012): many small tufts of real blades, bent by the wind in the vertex shader, thinned by distance so a field costs what the near part costs.

- **The "grass" mesh** (mesh3d.h mesh3d_grass, a built-in like "cube"): one tuft, 9 blades of 4 segments each, each blade leaning and curving out from the root, double-sided, 1 m tall standing on y = 0. Vertex colours go from a dark root to a light yellowish tip; the normals lean up, so the tuft lights as a field does rather than as thin cards.
- **Wind** (mesh.vert, the uniform's `wind`): each copy's place gives it a phase, so gusts run over the field as waves. A vertex moves by the wind times its height squared (in the mesh: tips most, roots never) times the copy's scale. A layer's `wind` 0..1 is its strength; 0 turns it off (rocks).
- **Fade** (the uniform's `eye`): up to a layer's `fade` metres from the camera every copy is drawn; between fade and 1.5x fade each copy goes at its own distance (a hash of its place), and past that none. A gone copy's vertices are put outside the view, so the GPU clips them. 0: never.
- G3Item has `sway` and `fade`; the draw order and the runs split by them, so each layer is still one instanced draw per part.
- The time is the editor's clock (SDL_GetTicks), so the wind moves while paused too; the CPU rasterizer draws the tufts still and whole.
- **The foliage editor in 3D:** host_view3d takes `foliage = items, area = { w, d }, time`: editor.c caches the arrays per view (by the items table) and render.h lite3d_draw adds a floor and every copy. The tab starts in 3D (orbit with LMB, wheel zooms, double-click resets); "Above" is the old map. It redraws every frame only while a layer has wind.
- Not done (Outerra's other half): blades generated on the GPU from a density texture, with no per-copy data at all; terrain-following placement; grass shadows (tufts cast them, but self-shadowing is coarse).
